feat(DOD-017): idempotency keys at the write boundary

DOD-017's recorded gap was "no retry/reorder/delayed-delivery semantics, no
idempotency KEYS at the API boundary, no commit/ack fault injection". Closing it
found a real defect: record_conception minted a NEW UUID per call, so a
transport-level retry -- the client never learning whether the first attempt
landed -- stored the same invention text TWICE, under two ids and two audit
entries, with nothing in the response to say so.

- Vault::put_conception_event_keyed returns IdempotentWrite::{Recorded, Replayed}:
  a new key is recorded; a key replayed with the SAME content is a no-op naming
  the event the FIRST attempt stored (created_utc not restamped); a key replayed
  with DIFFERENT content is refused as IdempotencyConflict, naming the key and
  both fingerprints, because a key that maps to two payloads makes reconciliation
  worthless.
- commands::record_conception_keyed reports `replayed` and "nothing written";
  registered over IPC as record_conception_keyed and logged on the dashboard.
- Tests cover every term the clause names: retried (replay, same event, no new
  work), duplicate (three submissions -> one event), reordered and delayed (three
  keys out of order -> three events), concurrent (four threads from a barrier ->
  one event, all callers naming it), commit/ack fault (a refused write leaves no
  row and the key stays usable), and integrity (conflicting payload refused).
- Across the packaged artifact over real IPC: first write replayed=false, retry
  replayed=true naming the same event, ledger 3 -> 3, conflicting content refused.

MUT-DOD-017-a (every keyed write reported as freshly recorded) and
MUT-DOD-017-b (a different payload accepted under an existing key) are both
CAUGHT and restored; twelve controlled defects now run.
